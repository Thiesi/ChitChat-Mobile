# M5c2b: native room reactions

Consumes delivered [M5c2a room state](M5c2a-room-reaction-state.md), PR67/main `4e9bc85`, and the unchanged [M5c1 protocol](M5c1-reaction-protocol.md). Authenticated room members can open Reactions from message actions or a retained reaction chip, choose among the exact six emoji, inspect complete reactor lists, and explicitly recover an unconfirmed change. DM reaction controls/state, guests and live/device/release acceptance remain separate. In-app availability copy distinguishes room reactions from those gaps.

## Presentation and consent

Each fixed choice says Add or Remove with its name and current count. Selection comes from the viewer's ID in the reactor list, including shared actor-perspective events; a chip opens choices and does not silently toggle. Modal choices and chips have48dp targets. Choices and the full people list scroll inside the dialog; status/recovery also remain reachable through room Details when the main header is collapsed. Reactor names are rendered as text, never logged, persisted or used for authorization.

The feature owns the original session, navigation entry, selection/request and canonical row. The shared message-actions addition is an optional presentation callback; DM consumers receive no new action. Root entry/lifecycle/covering-modal guards bind every callback. The room actor remains the only write owner; no duplicate transport/job, focus/IME repair, readiness wait, test-tap replay or new saved state is introduced. Opening/closing the picker suppresses read/typing and retires live-edge proof. A fresh actual viewport is required after closing. Genuine navigation/background drops selection while retaining unknown writes; configuration recreation retains the ViewModel operation, with no new POST.

A POST failure can follow commit. Every ordinary Add/Remove stays disabled while that original uncertainty exists. Check history performs GET only; a retained picker then requires explicit Review before a fresh Add/Remove choice. Closing does not clear uncertainty, and reopening is blocked until its explicit check. General refresh and passive canonical replacement are not replay consent. A newly received canonical row may be explicitly reviewed into a NEW request; it never gives an old callback new authority. Unknown/ignored policy hides private picker rows immediately. SEND/READ and author-change uncertainty remain independent.

## Deleted-row decision

Retain the existing native transcript's reaction data on tombstones. The pinned browser room renderer hides its bar on deleted rows, while the later DM renderer and reaction hydration differ; that historical presentation is not a server prohibition on removal. Both services allow otherwise-authorized own removal after deletion/mute. This native consumer therefore keeps existing counts/selection visible and permits withdrawing one's existing reaction, with every new add disabled. The picker explicitly discloses that reaction counts/names may remain. It never restores a deleted body, quote, Copy/Reply or author action. This is a deliberate client presentation choice using the unchanged server authorization contract, not a backend patch or a promise to purge retained data.
