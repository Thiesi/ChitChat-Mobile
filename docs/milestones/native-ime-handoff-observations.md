## Additional observations

The existing `androidTest`-only `NativeInputWindow` now samples native touch mode and IME controllability alongside its focus/inset scalars. This distinguishes additional input-mode/window-control hypotheses in a future failure without guessing a production correction.

- Touch mode uses the native View getter. No focus-flushing IMM getter is called.
- On API30+, an ephemeral [controllable-insets listener](https://developer.android.com/reference/android/view/WindowInsetsController.OnControllableInsetsChangedListener) records only an IME Boolean and is removed in `finally`. Missing controller/callback, older API or an observation failure remains null, never fabricated false. It does not wait for a callback, request animation control, change visibility or retain a View/controller in the result.
- Controllability is **not** a keyboard-readiness predicate or a guarantee that an IME request will succeed. Do not add it to production input/send gates or replace positive visible-IME proof with it.
- Sampling adds UI-thread work and can affect timing. A later pass is not a root-cause fix. The original one physical tap, focus/visible-IME assertion and5-second deadline remain unchanged.
- Only scalar results are retained; no editor contents, titles, credentials or private objects. The existing narrow CI trace filter and failure status remain unchanged; no raw logcat/dumps, new dependencies, live server calls or integration-file access.

Instrumented coverage checks scalar-only results/canary exclusion and observes focus/insets before sampling and after a deliberate real input tap. API26 controllability remains unknown; this does not claim API26 device acceptance.

The first full run showed both observed flags true before/after the failed tap. A second, test-only layer can observe the public Compose input-session pipeline in the shared fixture root: bounded64 fixed-kind/timestamp/session-ID events for start, connection request/creation/failure and end. It always delegates once, returns the original connection unchanged and rethrows original errors. EditorInfo/connection contents are never read; original requests are referenced only for normal session-scoped delegation, never stored in records. A stable remembered interceptor prevents the observer itself restarting input on recomposition. Original-reference disposal cannot retire a newer fixture's recorder. Only failure assertions include the bounded scalar event summary; absent instrumentation is distinguished from an observed empty history. No raw trace-filter expansion or production API change.

Shared-root interception is **off by default**. Enable it only for a separately labelled diagnostic invocation with instrumentation argument `-e traceNativeInput true`. Normal CI/full native gates must omit that argument and exercise the original input pipeline. The standalone observer journey explicitly installs it to verify delegation/lifetime, independent of that flag. Even correct delegation adds a framework layer and can change timing; a traced pass is not equivalent to an untraced gate or a correction.

New coverage checks bounded/scalar records, stale-root disposal and real connection delegation without session restart on parent recomposition. Android may create multiple connections within one session; those callbacks are not misreported as a new session. This remains timing-affecting observation, not a correction.

## Source investigation, not a dependency fix

The resolved UI/Foundation versions are1.11.4 (BOM2026.06.01). Inspection of their official Google Maven source jars follows the legacy adapter through the public input session into the native owner. Session cancellation and queued visibility requests must be distinguished from a simple recomposition; the adapter, field state and interaction source are remembered. No observed record yet establishes that ordinary recomposition restarts the failed session. The probe's parent-recomposition journey checks its own stable interceptor, not every production navigation path.

The resolved Core keyboard implementation is1.16.0. Its `SoftwareKeyboardControllerCompat.java` and1.17.0's are byte-identical in the downloaded source jars. The API30 implementation invokes both the insets and legacy show paths; duplicate platform request tokens alone are therefore not evidence of a client bug. No relevant correction was established by that comparison, so no dependency upgrade, IMM focus-flushing getter, window soft-input flag change or state-based field migration is presented as a fix. The WindowManager cancellation phase likewise is a symptom, not a diagnosed cause.

A dedicated physical-device comparison uses the fixture APKs and strict single-tap cases without server credentials, network fixtures or integration-file access. Check device/Android compatibility and avoid replacing an existing user's installation or changing global keyboard/rotation settings implicitly. The maintainer supplied a wireless-debugging device reporting Android17/API37. Its active user was explicitly selected; the initial package query across profiles was denied by Android and was not bypassed. No existing active-user development package was present; both APKs were newly installed without replacement permission, scoped to that active user. Other profiles, global keyboard/display settings and screenshots were not accessed or changed. This OS/device comparison is not evidence of an API36 correction.
