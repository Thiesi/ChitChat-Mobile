# M4c4c1: account-scoped notification-center state

This prerequisite adds bounded canonical notification windows and presentation state over the existing [M4c4a HTTP contracts](M4c4a-notification-contracts.md). It does not add a native center, unread badge, navigation controls, push receiver or new server endpoint. Those native consumers follow separately; a successful state/API test is not a usable notification center. Existing [same-conversation quote navigation](M4c4b2-native-reply-targets.md) remains intact.

## Product and backend semantics

The pinned browser [renders View message and Mark as read separately](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/public/assets/js/privacy-notifications.js#L138). Listing or opening a destination does not implicitly read a notification, and reading a notification never acknowledges room/DM history. All remains an explicit choice that includes unloaded notices and notices arriving before the server processes it. The independent server unread count is not calculated from the loaded subset; `updated:0` is valid.

`NotificationCenterViewModel` captures the original rendered server/account/generation/session version for page and read operations. Member lifecycle/state is main-confined and memory-only. Guest visitation remains the separate M7 consumer; no backend authorization is changed. Original callbacks and confirmation references cannot act on another account or clear a replacement confirmation. Genuine background retires work and confirmations; clearing the owner additionally drops private rows/counts and prevents reactivation by stale callbacks. Configuration-preserving lifecycle wiring belongs in the native consumer.

## Canonical windows and read operations

The shared row validator checks the existing descending, unique positive IDs, exclusive bounds, timestamps, literal read/read-at consistency and nonnegative count. The canonical reader follows at most six pages of 100 rows, preserving the caller's original session closure. Its coverage/bounds are client-derived, not server snapshot fields. Rows fetched below the captured lower boundary are excluded without skipping them on the next More action. Missing coverage is explicit and never stitches an unrelated newest page into old cached rows.

Presentation memory is bounded to 500 notices. Explicit older pagination shifts the window without silently widening it on retention loss; its fixed upper bound survives a completely empty historical range across resume, hints and ordinary Refresh. Latest is a separate explicit action. No content enters saved-state bundles, disk caches or generated state strings.

GETs and read POSTs are serialized. Invalidations queue/coalesce behind a POST rather than cancelling it. A confirmed response updates the independent count and a local read-ID overlay before canonical GET reconciliation; no fabricated server `read_at` timestamp is added. If that GET fails, the confirmed POST remains confirmed and visible through its overlay. An unconfirmed or background-cancelled POST retains unknown-read state. Passive foreground/hint GETs cannot clear it or replay ids/All; a successful explicit GET lets the user inspect current state and choose a new read action. Safe More pagination remains available after passive GETs make the range fresh, without granting another mutation or clearing unknown state. All requires its original explicit confirmation. The next UI must explain this distinction and provide Refresh, session/rate/error states and Latest when coverage is incomplete.

Confirmed resource denial clears private content/counts; CSRF/network failures do not pretend the resource was revoked. No guessed notification SSE event, permanent timer/connection, background worker, parallel cookie jar or Firebase configuration is introduced. The existing session repository still owns HTTPS, cookies, CSRF and authorization errors.
