# M5g5e: original-bound DM upload actor core

This connects retained upload ownership to the real DM owner. No native picker,
attachment card, privacy choice, download or sharing feature is added. UNKNOWN
remains locked until the separate DM history/evidence/duplicate-risk consumer.
Files/media is not usable and existing availability disclosures remain accurate.

## Admission and serialization

Fresh Send requires the original actual entry/STARTED/root-modal permission,
foreground owner, peer, exact current READY selection/slot and completed source
handoff. Freeze the original session, content token, literal PHP-trimmed caption,
reply, final-byte SHA and start time. Empty captions are valid and slash commands
stay literal; retain the4000-codepoint cap. Current DM privacy, relationship,
mute/block uncertainty and final-byte file policy must allow the operation.
Room ignore IDs grant no DM restriction or permission.

The real MainActivity factory injects the same process SessionAttachmentRepository
used by rooms. UPLOAD is a distinct marker in the existing serialized DM job;
it excludes SEND/READ/BLOCK/AUTHOR/REACTION and canonical GETs. There is no second
unserialized POST job, new client/jar/dispatcher, upload queue or automatic replay.
DEFAULT/LAZY cancellation before entry is accounted for with no transport call.

The concrete direct transport revalidates the current DM disclosure after original
access and file-policy checks. An older rendered valid snapshot cannot authorize
upload after current privacy disappears. Missing/invalid facts produce the existing
safe compatibility failure before a POST. This adds no implicit bootstrap/GET or
new server policy; server authorization remains authoritative.

## Lifecycle and resource ownership

An already-authorized upload survives navigation to the inbox, another peer or
another app route. Root callbacks distinguish actual entry departure from genuine
background, including a paused upload while the inbox/home is current. Invalid
scope cannot provide a screen lifecycle owner; the root background hook covers it.
Configuration retains VM work and skips genuine-background cancellation.

Genuine background cancels while preserving serialization until actual callback
AND writer stop. An old owner closes its draft handles and detaches its marker,
so a successor can work; its physical transport charge remains until stop. Late
results/finally cannot clear successor busy state or repopulate retired drafts.
No global budget reset, provider reopen or premature byte release is introduced.

DirectDraft content tokens preserve edit-away/back, and preparation-only progress
retains the same discard choice. Remove/Replace/inbox discard cannot cross upload
attempts or newer content. Pending/file-only/unknown drafts count against100 slots;
there is no eviction. Completed job/observer/entry-probe references are cleared.
Long-lived attempt metadata contains no payload or full session snapshot; debug
strings remain opaque and no content/digest enters saved state or logs.

## Outcomes and independent consent

Buffered file100% is not full multipart completion. Finishing uses actual full-body
facts; a held Cancel rechecks them. Cancellation alone proves nothing. Only actual
stop with an attempted upper bound smaller than the whole body returns READY.
A possibly complete throwing final chunk or full-body interruption stays UNKNOWN.
Definite refusals retain the same file/caption/reply and safe server metadata;
local file-policy refusal remains distinct from server rejection.

Validated201 is private CONFIRMED before any GET. Bytes release after actual stop;
fresh original-entry adoption clears only the original file/content token, keeps
newer captions/replies, and records the known ID before canonical refresh. GET
failure never recreates uncertainty or a synthetic message. A departed entry's
ACK waits privately for fresh adoption. Existing canonical history supplies bubbles.

Automatic entry/refresh/text duplicate-risk controls cannot unlock UNKNOWN or let
the caption bypass file state as a text send. No DM upload history/consent API ships
in this slice. Positive-ACK GET uses consent=false and reconcileBlock=false;
SEND/READ/BLOCK/AUTHOR/REACTION uncertainty remains independent. Upload completion
and navigation retire old viewport proof; only a fresh actual viewport may cause
the existing whole-peer read. The following DM review must preserve these boundaries
and the clock-domain decision tracked in [184](https://github.com/Thiesi/ChitChat-Mobile/issues/184).
