# M5c2a: serialized room reaction state

Starts from delivered [M5c1](M5c1-reaction-protocol.md), PR64/main `45dafd0`. This independently buildable slice consumes its existing protocol in the room ViewModel. The native picker/chips and recovery controls, DM actor, guest behavior and live acceptance remain separate. Existing in-app disclosures continue to say reactions are unavailable: no user control is exposed by state groundwork.

## Original choice and operation ownership

An in-memory request holds the original rendered session and exact canonical room-row instance. It requires a foreground authenticated member, known current policy and a current visible/revealed row. Selection derives from the viewer's presence in reactor IDs, never another actor's `reacted_by_me` flag. A choice is explicit add or remove, never a toggle. An already-satisfied choice does nothing. Adds require a non-deleted row and current room/account mute permission; removing the viewer's own existing reaction remains possible while muted or on a retained tombstone. This is state capability only, not a decision to expose a deleted-row picker.

Reactions and author mutations share the room's bounded mutation job and existing busy/sequence gate. Active read/send/author work prevents a reaction POST; hints queue/coalesce behind it. Navigation/target adoption must reject the active reaction and its selection instead of cancelling a POST. Pending choices cannot be changed or dismissed. Every await and response is fenced by the original owner/room/operation; stale callbacks and same-ID replacement instances gain no new authority. Confirmation replaces only the original row's complete reaction summary, preserving its content, quotes, metadata and author capabilities. It retires the pending marker before fallible canonical GETs, so a failed refresh cannot turn a confirmed write into uncertainty.

Opening/closing selection clears live-edge proof; room send, stale draft edits, read acknowledgments and other message actions are blocked by the selection. The existing conversation modal observation also suppresses read/typing publication. This adds no focus request, IME action or keyboard workaround. The separate native consumer must supply actual root entry/lifecycle/window modal guards and accessible controls before exposing these methods.

## Unknown outcomes and explicit recovery

Any exception/cancellation after a POST begins can follow commit. Retain only room ID, message ID, emoji and desired Boolean in the account/server/generation/version-owned map: one uncertain choice per room, maximum100 rooms, no eviction. There is no body, reactor name, saved-state/disk persistence, retry queue or automatic POST replay. Capacity is reserved before starting and released by an explicit successful history check; other rooms are still usable until the fixed bound is reached. Background/navigation preserves uncertainty but drops selection; owner retirement clears private state. Late responses cannot populate a successor room/account.

Passive entry, general refresh, invalidation and a successful unrelated operation never clear reaction uncertainty. Only the original unknown-reference explicit GET can reconcile it. A retained selection becomes checked and cannot POST; an explicit Review creates a fresh request from the NEW canonical row before another fresh desired choice. A dismissed selection is not recreated by recovery. Failed GET retains uncertainty. Canonical history/window rules retain fixed upper bounds and draft/unknown-send state; reaction GET/Review gives no SEND/READ or author-change consent. Scoped resource denial clears inaccessible content while retaining unresolved writes.
