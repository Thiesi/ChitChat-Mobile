# M2b1: native registration and account restoration

This buildable M2b slice adds registration/restoration, not completion of M2 or the application. The separate M2b2 slice still owns shared sensitive-action step-up. Android base was fetched and matched `origin/main` at `dd3faae8` before branching. Backend `main` remains the audited v3.2.1 / `4f53ff4`; the sibling checkout is read-only and differs only by its pre-existing mobile ADR.

## Contracts and implementation

- `public/api/v1/registration-challenge.php` issues a session-bound challenge; `src/Auth/RegistrationChallenge.php` uses a 32-hex nonce and SHA-256 of `nonce:decimal_counter`. Verification consumes the challenge even on validation failure; earlier endpoint rate/type checks can reject before verification. The client conservatively treats every submit as single-use. `src/Admin/RegistrationProtectionService.php` and `src/Config.php` bound difficulty to 0–22. A null challenge means no proof is required. Native computation is off the main thread, cooperatively cancellable every 256 hashes, bounded to 60 seconds, and stopped on background/form cancellation. Nothing is persisted or logged.
- `public/api/v1/register.php` returns **201**, not generic200 success. It receives username/password/optional ISO birth date, empty `website`, and exact challenge fields. The server alone assigns first-account roles. Native validation mirrors `src/Auth/Username.php`/`PasswordPolicy.php`; server errors remain authoritative. The server does not advertise minimum fill time, so the app does not invent a delay or automatically replay failed POSTs. Any failed submit requires an explicit fresh proof; ambiguous results warn that the account may already exist and suggest sign-in.
- `public/api/v1/account/restore.php` restores only an account awaiting closure before its deadline. It is not password reset. **202** means restoration remains pending MFA; no authenticated UI or saved credentials are published. `public/api/v1/mfa/login-recovery.php` completes the same server-bound restore flow. The client requires explicit restoration confirmation before displaying success. Closed/deadline/not-pending/banned cases have distinct explanations. Native passkeys/provider handoff still require B1/B2.
- The existing origin/cookie/CSRF/vault/generation architecture is reused. No parallel auth client or guessed endpoint was added. Late challenge/register callbacks cannot overwrite another form/logout; challenge refresh honors rate limits. Server changes are disabled during a submitted mutation. Passwords/confirmation are cleared at submit/background; optional birth date stays only in the active form and clears on background. The date picker uses a non-saveable state factory and disables its children's saveable-state registry. Errors are announced and brought into view in long forms.

## Acceptance boundary and next work

Normal tests never read `.env.integration`; only the existing explicitly invoked live task uses the ignored, user-owned dedicated account. No credentials are printed, committed or sent to CI. Live creation/closure/restoration of a disposable account needs maintainer approval; no such account mutation has been performed for this slice. Fixture success is not live registration/restoration, MFA/passkey or native password-UI acceptance. No release signing, chat, SSE or push completion is claimed.

After this slice, implement M2b2's reusable password/recovery step-up flow with one explicitly authorized protected-action retry, cancellation/background/logout isolation and honest B1/B2 fallbacks. M3 then implements rooms and foreground SSE. Keep M2 unchecked until its remaining slice and acceptance boundaries are recorded.
