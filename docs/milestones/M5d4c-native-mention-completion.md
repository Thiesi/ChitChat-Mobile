## Original pane, draft and selection

`CompletionViewModel` owns one active pane and only safe GET jobs. Pane/selection/request references bind original server/account/generation/session version, room-or-peer namespace, actual navigation entry ID and complete editor snapshot. Root lifecycle and actual current STARTED entry control activation/navigation. Old owner, entry, target, peer-name, choice, candidate, error, finally, close and retry callbacks cannot replace successors. A rejecting draft consumer keeps its choice; a reentrant accepted consumer cannot have its successor cleared by the old callback.

The25-member seed is attempted once per original pane; failure leaves local speaker/presence fallback and is not replayed by repeated bind/foreground. Prefix lookups debounce actual edit/caret changes by150ms, cancel only obsolete GET work and require explicit Refresh suggestions after failure. Passive foreground, configuration restoration, identical field echoes and canonical draft updates do not manufacture prefix requests or typing input. Configuration retains the original VM work; UI may restore a caret at draft end, and an old selection is usable only if the whole editor snapshot still matches. Genuine background, owner retirement and navigation drop private choices/member hints, never canonical drafts or POSTs.

Token/application logic uses UTF16 editor offsets, exact token-at-caret boundaries, unchanged complete prefix/suffix and collapsed selection only. Active IME composition is preserved and suppresses completion; moving selection alone grants no typing consent. A final newline is after the token, not its old caret position. No content, names, queries, pending work or editor selection are saved to bundles/disk/logs. Private-bearing objects have no generated content string representation.

Feature-owned `updateDraft(originalSession, roomOrPeer, wholeText)` remains the only canonical writer. The UI bridge additionally checks the current complete canonical body/editor and actual entry/modal context before committing. It preserves retained reply selection, send uncertainty and explicit reconciliation/duplicate-risk flags; choosing a name cannot send, read, block, change policy or authorize a notification. An identical body on a different owner/entry never revives an old choice.
