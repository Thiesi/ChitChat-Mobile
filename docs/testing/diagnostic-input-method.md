# Test-only framework input-method control

This is an explicit diagnostic control, not an application keyboard or a production fix. All source/resources/manifest entries live in `app/src/androidTest`; the app APK must contain neither the service nor its declaration. The service requires Android's signature `BIND_INPUT_METHOD` permission, runs in the test package's `:diagnosticIme` process, and is never selected automatically. Normal CI retains the stock keyboard and all existing input assertions. Three inert tests verify manifest/process protection, absence from the app, and the callback-log bound, bringing this branch's normal native total from195 to198.

## Control and observations

The service supplies a native200dp panel with Space/Delete buttons. They write only after an explicit button click; the service never reads surrounding/editor text, stores EditorInfo or connections, accesses the network, or requests/repairs focus or IME visibility. Its only additional observations are lifecycle/root-visibility callbacks. Super implementations are delegated normally, without retry, extra show/hide, timer or readiness gate.

The `ChitChatTestIme` log contains only `n=<ordinal> t=<uptime> e=<fixed enum>`. At most1024 events plus one LIMIT marker are emitted for a service instance; later callbacks are omitted. Treat a limit/restart/capture gap as missing evidence, never an absent event. No body, editor field, package/username, connection, exception, raw fallback or arbitrary label is logged. The default full gate does not opt into this service or tag.

Adding lifecycle observations, replacing a complex keyboard with a minimal panel and changing a process are experimental interventions that can change timing. A passing alternate-IME arm is non-reproduction and cannot attribute the default failure to the keyboard. A failure helps establish that this particular bundled implementation is not necessary. Even a positive comparison is not device, default-keyboard or release acceptance.

## Fixed local experiment and safety boundary

After builds/artifact isolation pass, use two NEW matched owned API36.0 revision7 emulators, sequentially: first bundled/default IME, then this diagnostic IME. Use the same new app/test APK pair, same software renderer/WHPX/display/heaps/font/animations/rotation settings and package-verify preparation. Record exact source/APK/signer/environment and default/selected IME identities; require a restored original IME before stopping the second guest. Selection is a device-level test setting, not an instrumentation parameter or production behavior.

Each arm gets two fixed10s CPU samples; either above80% aborts setup without polling until quiet. Cold boot has1200s bound from launch. No fixture warmup, input-session tracing flag, observer override, extra rounds or phone/autofill override. Select the original standalone100-cycle method once per arm, with `expectSoftKeyboard=true`,600s outer bound, unchanged physical tap/focus/display/positive-IME/5000ms assertions and first-failure behavior. Both arms are predeclared; native failure alone does not cancel the other planned arm. Setup/source/identity/capture-integrity failure or host timeout aborts remaining work. No failed arm is replayed to seek green. This is a new keyboard-implementation comparison, not a rerun of the completed renderer pair.

Explicit serials and verified AVD names are mandatory. Never select/enable this service on the connected phone, an existing AVD, an account-bearing device or ordinary CI. No live server, `.env.integration`, keyboard-manager changes, broad raw logs/dumps or unrelated UI. The ignored launcher reuses the existing allowlisted collector; any additional service callback parsing must accept only the fixed enum/scalar grammar and preserve bounds/gaps. Record all negatives and terminal method identities/counts; ADB0 alone is insufficient.
