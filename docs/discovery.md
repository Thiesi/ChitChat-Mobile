## Findings that determine the design

1. **Use the existing session architecture.** Cookies plus CSRF work with a native HTTP client. The app does not need Firebase Authentication, JWTs, a refresh-token service, or a second chat backend. `session.php` establishes an anonymous session and reports authentication, policies, preferences, guest access, providers, and lockdown. Every mutation carries its CSRF token. Login, MFA, password changes, and logout rotate or invalidate state. See [the verified contract](backend-compatibility.md).
2. **Core chat is implementable now.** Existing APIs cover room discovery/membership, history, sending, replies/mentions, pings, reactions, edits/deletes, DMs, read state, files, search, presence, typing, guest mode, reporting, moderation, and administration. No feature is omitted just because it has an administrative browser page. The [parity matrix](feature-parity.md) assigns each surface to a milestone.
3. **Native passkeys require backend work and operator configuration.** The server accepts one exact configured browser origin. Credential Manager uses an Android signing-certificate origin; a normal app cannot impersonate the browser origin. Each server must trust the intended app certificates and publish Digital Asset Links for its RP domain. Preserve password-first MFA, user verification, RP checks, and single-use session-bound challenges. Recovery codes already work but are finite emergency credentials, not a routine passkey replacement. [Source](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/Auth/WebAuthnProtocol.php#L188), [Android server-origin guidance](https://developer.android.com/identity/passkeys/create-passkeys), [Digital Asset Links](https://developer.android.com/identity/credential-manager/prerequisites).
4. **Google/Twitch need a secure browser-to-app handoff.** Existing provider flows use server-held PKCE, nonce/state, and browser PHP cookies, then redirect to web pages. Custom Tabs do not authenticate the app's HTTP cookie jar. This affects sign-in, provider account creation, linking, provider step-up, restoration, and profile-picture import. Propose a short-lived PKCE-bound result exchange into the existing native PHP session; never copy browser cookies or return a session secret in a URL. [Source](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/Auth/Oidc/OidcService.php#L25).
5. **Foreground SSE needs explicit reconciliation.** Streams close after about 25 seconds, with 10-second heartbeats and a one-second suggested retry. IDs support deduplication and replay; event retention and permission filtering mean replay cannot restore all state. No cursor-expiry reset or snapshot-plus-cursor API exists. Use latest history plus bounded older-page traversal and visible-message mutation/attachment refresh; show discontinuities honestly. Missing around-message lookup is a performance limitation, not a reason to invent an endpoint. [Realtime contract](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/docs/api/realtime.md).
6. **FCM is absent.** Existing Web Push requires `endpoint`, `p256dh`, and `auth`; an FCM token is none of these. Its sender sweeps durable notifications and marks a shared `push_dispatched_at`, even on suppressed/failed delivery. A second sender cannot safely reuse that one global dispatch marker. Separate device lifecycle and delivery work is required. [Subscription API](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/docs/api/web-push.md), [dispatcher](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/WebPush/WebPushDispatcher.php#L127).
7. **Ordinary incoming DMs currently do not create background notifications.** Targeted SSE and unread counts exist. Mentions inside DMs can create `mentioned` notifications, but an ordinary DM is not a durable notification category. Adding DM push requires an explicit product decision and new backend behavior, including preferences and duplicate suppression; it is not existing feature parity.
8. **Privacy disclosures must follow the live server.** DMs are not E2EE; deletion/editing retain revisions; retention and inspection are installation-dependent. `session.php` currently returns `privacy.message_revisions.participant_notification: false`, while revision-review documentation/service behavior describes participant notifications. Display the server-provided policy and established retained-content warning; record this discrepancy for backend clarification, without promising a disclosure the capability field denies. No client should infer full privacy policy from an old ADR alone.

The older [mobile-strategy ADR](https://github.com/Thiesi/ChitChat/blob/d4d60d8eb6d802170fc16f2353f628b3269abcd3/docs/architecture/0007-mobile-app.md) recommends a PWA and deferring native administration. Those proposals are superseded for this Android repository by the assignment. Its suggestion that token authentication is a prerequisite is not supported by the current HTTP contracts. Its push-relay concern is real, but a relay is a distribution choice: matching operator Firebase builds or explicit delegated sender authorization are also possible. Broad publisher-project send permission on arbitrary servers is not recommended.

## Recommended architecture and delivery

[Architecture](architecture.md) recommends one Compose app module with purposeful packages, ViewModels/StateFlow, repositories, Kotlin serialization, Retrofit/OkHttp plus an SSE adapter, a secure cookie/CSRF session manager, a Room-backed encrypted content cache, DataStore for non-secret settings, and WorkManager for bounded push registration tasks. The system browser is restricted to authentication handoff. No WebView, foreground connection service, or background polling loop.

Start with one active server/account and explicit sign-out before switching. HTTPS is required for production. Android 8/API 26 is the proposed minimum; Credential Manager passkeys require a supported Android 9+/provider configuration. Select compatible stable compiler/SDK/library versions during M1 and pin them; do not adopt an alpha merely because a documentation sample uses it.

[Implementation milestones](implementation-plan.md) are vertical slices with gates and a commit/PR each. M1-M5 can proceed without the native-auth/FCM backend changes; M6/M7 implement supported account/admin flows while accurately labeling pending native-origin or browser dependencies. M8 is the real-installation acceptance and release gate. FCM client tests do not close server or device-delivery dependencies.

## Consequential decisions for the maintainer

These are proposals, not accepted decisions. Routine library/package-layout choices do not need approval.

| Decision | Recommendation | Alternatives and implications |
|---|---|---|
| Push delivery for one app connecting to arbitrary self-hosted servers | A publisher-operated, opt-in relay with authenticated instance enrollment, per-device authorization, quotas, and content-free payloads; keep a direct sender adapter for operator builds | Operator-owned Firebase builds avoid a central relay, but each build and its server need the same project and users cannot expect one universal APK. Delegating publisher-project send IAM to arbitrary operators grants excessive authority. Relay hosting, operational ownership, and metadata disclosure require agreement before implementation. |
| Notifications for ordinary incoming DMs | Add an explicit opt-in DM category through the backend issue, default off until chosen; preserve existing mention/ping/security behavior | Retain current categories only: full parity with the web notification model, but ordinary DMs cannot alert a backgrounded app. Do not silently opt everyone into a new category. |
| Public application identity and distribution | Confirm `io.github.thiesi.chitchat` as the application ID; begin with a signed sideloaded alpha, then prepare Play distribution | A different ID must be selected before Firebase registration/DAL/release signing. Play introduces a separate app-signing certificate, store policy/disclosure work, and publisher account configuration. No Firebase project or signing key has been created. |

Separately needed for integration acceptance: a non-production compatible HTTPS installation, test accounts with representative roles/MFA/providers, and an Android device or emulator with Google Play services for FCM. Do not send production passwords or Firebase service-account keys in chat. No supplied server address is assumed.
