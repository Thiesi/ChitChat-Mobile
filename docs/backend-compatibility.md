# Backend contract and compatibility

[M4c4c1](milestones/M4c4c1-notification-state.md) consumes the existing notification page/read contracts through scoped presentation state and bounded canonical GET reconciliation. Counts remain independent of loaded rows; View message and Mark as read stay separate. Its bounds/coverage/confirmed-read overlay are local state, not server fields or timestamps. No new endpoint, SSE event, authorization mechanism or backend checkout change is introduced; native center/general-link consumption remains pending.

Verified source baseline: **v3.2.1 / `4f53ff497f5572072fddad42d8ac3979e9cdf0d1`**. This is a source audit, not a claim of tested installation compatibility. Source links pin the baseline; proposed APIs appear only in [backend issues](backend-dependencies.md).

## HTTP bootstrap, cookies, authentication

Requests are relative to the selected installation's root `/api/v1/`; use actual `.php` routes. JSON success payloads are returned directly, not under a universal `data` envelope. Errors are `{"error":{"code":"machine_code","message":"explanation"}}`. `Endpoint::run` maps typed API exceptions and JSON errors; responses set `Cache-Control:no-store`. [Endpoint](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/Http/Endpoint.php), [response](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/Http/JsonResponse.php).

`GET /api/v1/session.php` creates/reuses the PHP session cookie and returns CSRF. Actual top-level fields are `csrf_token`, `user`, `preferences`, `ignored_user_ids`, `share_typing`, `muted_everywhere`, `sign_in_providers`, `pending_sign_up`, `guest_access`, `registration_enabled`, `lockdown`, `web_push`, `security`, `privacy`. User metadata includes ID/username/roles/session version and guest state/expiry. `web_push.enabled` and its VAPID key do not imply FCM support. Neither native capability version nor effective installation-name override appears in this response. `/health.php` returns configured application name and version, without the DB-backed name override. [Bootstrap implementation](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/public/api/v1/session.php#L41).

Send the current `X-CSRF-Token` on POST, including anonymous login/register/restore, searches, inspection and multipart upload. CSRF uses the same cookie jar as the request. Cookies have lifetime zero, configurable name and Secure behavior, HttpOnly and SameSite attributes; native bounded persistence is specified in [architecture](architecture.md#network-and-session-security). The server validates account/session version, bans and guest expiry on authenticated access. Do not assume CORS or browser SameSite supplies native client authorization; ordinary native HTTP does not need browser CORS permission. [SessionManager](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/Auth/SessionManager.php#L15), [CSRF header](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/Http/Request.php#L134).

Example existing request: `POST /api/v1/login.php`, body `{"username":"Alice","password":"<entered password>"}`. Non-MFA success returns user and new CSRF/session state. MFA success of the first factor is **202** with new `csrf_token`, `mfa_required:true`, `methods:["passkey","recovery_code"]`, not a logged-in user. Pending MFA is short-lived and bound to source IP, session/account/version; switching networks can require sign-in again. Existing recovery completion: `POST /api/v1/mfa/login-recovery.php`, `{"recovery_code":"<one unused code>"}`. Adopt CSRF rotations from responses and rebootstrap when needed. Never retry an unsafe operation merely because the CSRF header became stale. [Login](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/public/api/v1/login.php#L16), [MFA](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/Auth/MfaService.php#L58).

Registration has username/password/optional `birth_date`, empty `website`, and session challenge fields `challenge_nonce`/`challenge_solution`. Challenge response is `{"challenge":{"nonce":"...","bits":16}}` or `{"challenge":null}`. Solve SHA-256 of `nonce + ":" + decimal_solution` for leading zero bits, off main thread. Minimum fill-time is operator-controlled and not returned in the challenge; fetch when form opens and handle `registration_too_fast` without guessing a fixed server delay. Every submission consumes the challenge; refresh after failure. Guest challenge has no minimum fill time. [RegistrationChallenge](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/Auth/RegistrationChallenge.php#L41).

Password-only step-up uses `/api/v1/step-up.php`; MFA accounts require passkey or `/api/v1/mfa/step-up-recovery.php`. `step_up_required` is a recoverable protected-action state; direct password step-up on MFA can return `passkey_step_up_required`. Retain intent and retry only once after explicit successful verification. Account closure destroys the session; password change rotates version and current session. Native passkey and browser provider flows are genuine B1/B2 dependencies; recovery does not count as native passkey support.

Handle HTTP 400 validation, 401 invalidation, 403 `csrf_failed` or resource authorization, resource-specific 404, 409 policy/conflict, 410 retained/deleted file absence, 429 throttles, and 503 lockdown/unavailable configuration. Do not interpret every 403 as expired login or automatically rerun protected writes. Honor `Retry-After` when supplied; current JSON error contracts do not guarantee retry timing, so use bounded backoff and explicit UI rather than invented response fields.

Replies are server-resolved within the conversation. Unavailable targets are `available:false` with `message:null`. Mentions are resolved and authorized on the server; Android provides suggestions without creating notifications itself. Room reactions in shared SSE need viewer-ID recalculation. Block relationship contains only `blocked_by_me` and `messaging_available`. Ignore is separate room-only presentation/attention behavior. Retained revisions are not erased on participant edit/delete; attachment access disappears before physical retention cleanup.

M4a implements the [existing-session DM protocol prerequisite](milestones/M4a-direct-protocol.md), not native DM screens. Actual DM mentions have only `user_id`/`username`, and quoted targets have no room `type`; use distinct DTOs. History and inbox previews are enriched with current exact-ID mutations and file metadata. Omitted retained rows do not change raw pagination evidence. A confirmed201 send returns its validated ID before any fallible refresh. Read sends only `{user_id}` and may mark an arrival absent from rendered history; the consumer must refetch and maintain local unseen attention separately from server unread counts. Fresh bootstrap supplies non-E2EE/retention/inspection and separate revision-review policy; a missing disclosure disables DMs, not otherwise compatible room access.

M4b1’s [state prerequisite](milestones/M4b1-direct-state.md) uses those existing history/metadata operations for bounded canonical windows with one original session capability. Raw cursors progress through empty enriched pages; fixed upper bounds survive retention removing all rows. Read-race attention/extra-acknowledgment warnings are local deductions, not new server counts/cursors. Native viewport, navigation and event consumers remain M4b2.

M4b2 now supplies the [native inbox/thread consumer](milestones/M4b2-native-direct-messages.md), including original-session policy/bootstrap and canonical SSE/foreground reconciliation. It uses no additional endpoints and never interprets the absence of a block/read SSE event as unchanged state. Native read proof cannot turn whole-peer acknowledgment into a bounded atomic cursor; local attention remains explicitly separate. M4c typing/ignore/notification endpoints, M5 actions/media and M6 UnifiedPush remain separate compatibility slices. No live DM acceptance is implied.

The shared executor permits16MiB only for bounded room/DM history, DM conversation previews and mutation batches, still with25-second timeouts. PHP's [JSON encoder](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/Http/JsonResponse.php#L22) escapes supplementary Unicode into12-byte surrogate pairs:100 messages with4000-codepoint bodies and full quoted bodies can exceed9MiB without violating the API. Other small JSON/auth and every error response remain capped at1MiB; exports separately retain16MiB/120seconds. Excess bulk data fails explicitly without logging out or introducing an unbounded buffer. This is a client safety bound, not a server response-size guarantee.

M3b implements the room HTTP subset through the existing session transport; [source locations and verification](milestones/M3b1-conversation-protocol.md) distinguish it from realtime integration. History returns ascending, exclusive-before IDs without `has_more`; retain the raw cursor even when mutation enrichment omits unavailable exact IDs. Canonical tombstones clear body/reply/file details but retain reactions. `rooms/read.php` can return0 after retention or a cursor already advanced by another device. `rooms/pings.php` returns at most100 private sent/received pings, ascending in a separate ID namespace. Session ignore/mute/display policy must be refreshed before rendering; an absent required policy is an explicit compatibility failure. Message timestamps include PDO space-separated offsets, whereas pings use RFC3339; neither is interpreted in a guessed timezone.

Only `/me` and `/ping` are server commands. `/dm`, `/topic`, `/shrug`, `/help` are implemented by the browser through ordinary APIs/local behavior; port them intentionally. Formatting is ChitChat's restricted grammar, not arbitrary HTML or full Markdown. [Browser commands](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/public/assets/js/slash-commands.js), [formatting](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/public/assets/js/message-format.js).

Its HTTP200 Boolean is authoritative, not the requested value. Missing/null bootstrap values stay unknown; quoted Boolean strings are incompatible. Failed/cancelled changes need explicit session GET reconciliation, never POST replay. The setting is bilateral across rooms/DMs and all devices, not a notification toggle. Local monotonic receipt metadata bounds queued display; server8s expiry/browser6.5s display and4s attempts remain compatible. Original session scope and current privacy/permission rules gate foreground member consumers. Guest/native-live acceptance remains separate; no new backend capability is assumed.

## SSE, presence, and state recovery

`GET events/stream.php` authenticates via cookie and releases the PHP session lock before polling. Header `Last-Event-ID` wins over `after_id`. Stream duration is about 25 seconds, polling 500ms in batches of 100; comment heartbeat every ten seconds, `retry:1000`. [Stream source](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/public/api/v1/events/stream.php#L20).

Persistent frame:

```text
id: 1235
event: room_message
data: {"id":1235,"type":"room_message","room_id":42,"actor_user_id":17,"payload":{"message":{}},"created_at":"..."}
```

The empty message above illustrates nesting only; actual DTO fields come from room history. Persistent event vocabulary includes `room_message`, `message_deleted`, `direct_message`, `message_reaction_changed`, `rooms_changed`, `ping`, `typing`, `room_broadcast`, `global_broadcast`, `presence_changed`, `forced_logout`. Edits republish the canonical message ID; one transport event ID is not one new chat message. There are no verified DM-read or block-change events: refresh read/relationship state through existing HTTP APIs on entry/resume and after local actions. Unknown events must not crash the client. [Realtime docs](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/docs/api/realtime.md), [DM realtime vocabulary](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/docs/api/direct-messages.md#realtime-delivery).

There is also **unnumbered, unenveloped** forced invalidation:

```text
event: forced_logout
data: {"reason":"session_invalidated"}
```

Handle it before normal persistent-event parsing. The stream checks account validity on each poll. [SseEncoder](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/Realtime/SseEncoder.php#L33).

The M3c1 [protocol foundation](milestones/M3c1-realtime-protocol.md) also accounts for two implementation details: standard SSE readers can carry a previous ID into that unnumbered control; and `RoomListSignal`'s empty PHP array serializes as `payload:[]`, not only the conceptual `{}`. Persistent forced-logout payloads include the newly assigned `session_version`; an equal/newer freshly authenticated version is not invalidated by a retained old event. The unnumbered server invalidation remains unconditional. No foreground consumer or cursor-storage guarantee follows merely from implementing these protocol operations.

M3c2's [foreground runtime](milestones/M3c2-foreground-runtime.md) consumes these operations without a backend change, with an in-memory validated cursor and canonical invalidation hints rather than a snapshot guarantee. It validates actual room/ping/reaction/presence/broadcast payloads before acknowledgement. `room_message` can represent an edit, not just a new row; room reaction `reacted_by_me` reflects the actor, so future UI consumers must re-read canonical personalized metadata. `rooms_changed`/unknown additive events trigger reconciliation. Presence cleanup/renewal must not silently recreate a pruned room lease on background or network return. M3c3 will connect the directory/transcript and deliberate presence UI; M3c2 does not claim those screens current merely because SSE opened.

M3c3a's [canonical room-window reader](milestones/M3c3a-canonical-history.md) uses only existing exclusive-before history and exact-ID metadata enrichment. Raw pagination can advance even if enrichment removes every row. Fresh history, not metadata alone, updates attachments and off-window quoted summaries. Coverage/older-availability fields are bounded client deductions, not new response fields or atomic snapshot guarantees; the same original session capability fences the entire traversal.

IDs are globally ordered but not contiguous per user. Current membership is checked on event reads; public history before joining does not grant room realtime. DMs publish separate perspective-correct events to the two participants. `rooms_changed` and `presence_changed` invalidate/refetch. Typing expires after eight seconds; room/presence invalidations after one hour, pings after one day; maintenance separately prunes the ledger by configured retention. `Last-Event-ID` alone is therefore insufficient after backgrounding. [Event selection](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/Realtime/EventRepository.php#L96), [cleanup](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/Maintenance/CleanupService.php#L39).

Presence POST is `{connection_id:"<UUID>",room_id:42,interacted:false}`. Renew foreground leases, set activity true only for deliberate interaction, use `room_id:null` for leaving presence. Response includes `idle_seconds`, `warning_seconds`, `expired`, `lease_seconds`. Membership survives expiry; refetch aggregate users instead of synthesizing them from events. Typing posts contain only room or recipient ID; account `share_typing` is bilateral; the browser sends at most every four seconds and displays about six seconds. [Presence](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/docs/api/presence.md).

## Notifications, policy, account, and administrative authorization

[M4c4a](milestones/M4c4a-notification-contracts.md) consumes existing `GET account/notifications/list.php` (`before_id>0`, `limit1..100`) and CSRF `POST account/notifications/read.php` with integer `ids` (max100, empty/duplicate valid) or `{all:true}`. List rows are ID-DESC/exclusive-before; raw last ID/page size derive local cursor/more evidence, not a server snapshot. `unread_count` is independent of the loaded page. Read returns `updated`/`unread_count`; zero is valid, foreign IDs are ignored, and All includes unloaded/new arrivals at server operation time. These IDs/read flags are not room/DM read cursors. Original-session access, bounded JSON, actual Boolean flags, explicit error handling and no implicit POST replay reuse the existing transport. Native center/read UI remains pending.

The strict parser recognizes actual service-generated room/message/ping, numeric DM `user_id` (not identity-by-`peer_name`), account and future guest-registration links only on the selected HTTPS origin/port. It rejects traversal-normalized paths, credentials, duplicate decoded keys, foreign origins and malformed IDs; an unknown link does not discard the notice text. Parsing is not navigation or authorization. Existing room/DM history can fetch an exact target plus older context with `before_id=target+1` (omit before for maximum signed ID); validate the exact returned ID and reauthorize, never silently show latest as the requested target. This requires no invented around endpoint. [Room implementation](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/Room/MessageService.php#L52), [DM implementation](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/DirectMessage/DirectMessageService.php#L173).

Compatibility/security detail: notification rendering can include usernames and mute reasons even though introductory backend documentation says otherwise. Treat returned text/details as private, untrusted plain text; no raw chat-body or blanket lock-screen-safety inference is made. Native guest consumption and notification/push consumers are separate slices; no new backend dependency or event was added here.

[M4c4b1](milestones/M4c4b1-message-target-state.md) implements the GET/state prerequisite for those exact numeric targets through one original-session capability and the existing history/metadata endpoints. Verify exact ID AND room/peer/viewer namespace; missing/omitted targets are unavailable and tombstones remain available. The bounded page retains raw older cursors; ping targets use only existing latest100 records. Fresh bootstrap/disclosure is mandatory, current ignore/mute policy is rebound after final awaits/consumption, and room-ignore never becomes DM block. This adds no backend requirement, read acknowledgment, native target screen or notification navigation claim.

[M4c4b2](milestones/M4c4b2-native-reply-targets.md) consumes those unchanged contracts for native same-conversation reply previews. Exact target adoption is a historical window, not an acknowledgment/idempotency/presence authority. Missing IDs differ from same-resource403/404 access loss: only the latter retires the current inaccessible pane, still bound to the original request/account/room or peer. Normal CSRF errors remain recoverable without resource revocation. Both panes preserve current policy, drafts/unknown writes and fixed bounds after retention empties a range. No new server dependency or browser-session bridge is introduced; center/ping/cross-conversation links remain separate.

Notifications list/read are account-scoped, durable and independent of transport; IDs/read state differ from room/DM read cursors. Server renders bounded text/links. Existing Web Push subscribe is `{endpoint:"https://...",p256dh:"...",auth:"..."}`; **never send a raw Firebase SDK token there**. UnifiedPush supplies the actual endpoint/key fields and can use this contract unchanged with the existing VAPID/`aes128gcm` worker on compatible HTTPS-443 endpoints. The current notification payload is `{title,body,link,app_name}`; no guaranteed notification ID or native binding may be assumed. Mention/ping push preferences and quiet hours exist. Security/policy kinds cannot be individually muted server-side, but OS/device permissions still control delivery. The dispatcher suppresses and marks quiet-hour notifications dispatched rather than queueing them until morning. Preserve that behavior. Ordinary DM arrival has no durable notification kind. [Web Push API](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/docs/api/web-push.md), [dispatcher](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/src/WebPush/WebPushDispatcher.php#L127). See [push compatibility, custom-port defect and hardening](push-architecture.md).

Account APIs cover avatars, date/clock, ignore, password, identities, MFA metadata, export/closure/restore. Guest opt-in is per endpoint; guests may report room messages/read their notifications/ignore/open profiles, but cannot use DM/upload/search/account/admin. Preserve session-only lifetime and read/write room controls. [Guest contract](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/docs/api/guest-access.md).

Moderation queues expose exact submitted evidence within current role scope, not surrounding DMs or attachment-download authority. Native message/user actions should consume server moderation capabilities; hidden controls do not replace backend checks. Admin role replacement/reset/policy changes and exact DM/revision inspection require step-up; ordinary reversible moderation does not uniformly require it. Exact revision review and canonical DM inspection are separate configurable capabilities, each requiring a reason and successful-access audit. Retain policy disclosures and never infer permission from a role string alone. [Admin](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/docs/api/admin.md), [reports](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/docs/api/moderation-reports.md), [review](https://github.com/Thiesi/ChitChat/blob/4f53ff497f5572072fddad42d8ac3979e9cdf0d1/docs/api/message-revision-review.md).

## Compatibility policy

Initial source target is v3.2.1, not every historical `/api/v1` deployment.
